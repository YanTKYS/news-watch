# news-watch 改善・機能追加提案

調査日: 2026-10-24（日本時間）

対象: `2263c3d` のソースコード、README、既存テスト、保存済みデータ

自治体職員が「新着を短時間で確認する」「過去の事例を探す」「動向と出典を共有する」ための改善案。UI/UXに加え、購読・横断検索・データ活用・編集品質・運用と保守を対象にする。今回は提案書のみを追加し、アプリケーションは変更しない。

コードから確認できた挙動を根拠にしている。実ブラウザでの表示・支援技術による操作・利用者インタビューは未実施のため、操作の困りごとと期待効果は実装前に検証する仮説として扱う。

## 維持したい設計

- GitHub Pagesで配信できる静的構成。新しいサーバーやログインを前提にしない。
- 日刊ログを正本とし、検索インデックスは派生データにする構造。
- `textContent` と検証済みURLによる描画。検索語の強調表示などでもこの安全性を維持する。
- 全期間のAND検索、NFKC正規化、日本語IMEの変換中抑制、250msの入力待ち、50件ずつの追加表示は実装済み。再提案せず改善の土台にする。
- ネイティブの選択欄・`details`、フォーカス表示、ダークモード、動きを減らす設定への対応も維持する。

## 01. 日刊・検索を含めたURL共有と履歴操作

**現状と根拠:** [app.js](../app.js) の `parseHash` は週刊・月刊のみを扱い、日刊の月・並び順・検索語はURLに入らない。`setHash` は `history.replaceState` を使い、`init` 以外にURL変更を反映するイベント処理がない。週刊・月刊の直接リンクは既に利用できる。

**提案:** 日刊の年月、並び順、検索語もURLで表現する。検索URLの例は `#daily?q=LGWAN&order=desc`、通常表示は `#daily/2026-10`。書式は案であり、既存の `#weekly/2026-W42` と `#monthly/2026-09` は維持する。画面ごとに「リンクをコピー」を用意する。

タブ・年月の確定操作は履歴に追加し、検索中の連続入力は履歴を置き換える。戻る・進む・手入力によるURL変更に追従し、ブラウザの既定のスクロール復元を妨げない。不正な値や一覧にない期間は、その旨を伝えて最新の利用可能な期間へ案内する。

**受け入れ条件:** コピーしたURLを別のタブで開くと同じ条件が復元される。日刊→週刊→月刊の順に移動後、戻る・進むで表示と選択欄が一致する。日本語・空白・記号を含む検索語が往復できる。入力1文字ごとの履歴は増やさない。

**注意:** 検索語は共有URLやブラウザ履歴に残るため、機密情報を入力させる用途にはしない。クリップボードAPIが使えない場合はURLを選択・コピーできる代替手段を示す。

## 02. エラー画面からの再試行

**現状と根拠:** `showMonth`、`showSearch`、`startReview` などは取得失敗を文字列で表示するが、再試行ボタンがない。特に一覧取得に失敗すると選択欄が無効のままになり、選択中のモードボタンを押しても `init` のクリック処理は再実行しない。別モードへの切り替えや再読み込みが必要になる場合がある。

**提案:** 失敗した対象と「再試行」を同じ場所に表示し、現在の検索語・選択期間を保って必要な取得だけをやり直す。利用者向けには「週の一覧を読み込めませんでした」と伝え、ファイルパスなどの診断情報は補足に分ける。自動の無限リトライは設けない。

**受け入れ条件:** 一覧・本文・検索インデックスそれぞれの通信失敗から、ページ全体を再読み込みせず復帰できる。再試行中は重複操作を防ぎ、失敗が続けばボタンを再び使える。再試行中に別モードへ移動しても、古い応答が現在の表示を上書きしない（既存の `loadToken` による制御を維持）。

## 03. 省略された説明・補助情報の展開

**現状と根拠:** [style.css](../style.css) の `.desc` は3行で切り詰め、`.foot` は1行で省略する。[app.js](../app.js) の `renderCard` は補助情報の全文を `title` 属性に設定するが、明示的な展開操作はない。タッチ操作ではホバーに頼れず、説明文にも展開経路がない。

**提案:** 長い説明文に「説明をもっと見る／閉じる」を設け、取得日・テーマ・検索語は折り返しか補足欄の開閉で全文を読めるようにする。元記事へ移動する前に、検索結果由来の説明文の範囲で判断できるようにする。記事本文の取得は追加しない。

**受け入れ条件:** 幅320pxと文字拡大時にも横スクロールなしで全文を確認できる。短い説明に不要な展開ボタンを出さない。ボタンの開閉状態が支援技術に伝わり、開閉後もフォーカスを保つ。カード末尾の余白や高さは、展開時の可読性を優先する。

## 04. 検索と画面切り替えのアクセシビリティ改善

**現状と根拠:** [index.html](../index.html) の `#status` にライブリージョンはあるが、`renderSearch` はこれを空にし、結果件数を通常の見出し内に描画する。`showMore` はカードを追加し、最後は操作ボタンを非表示にするが、追加件数の通知やフォーカス処理はない。日刊では月が `h2`、テーマが `h4`、記事が `h5` で、検索結果でも共通の `renderCard` が `h5` を生成するため、文書構造に対して見出しレベルが飛ぶ。

**提案:** 検索完了時に「検索結果12件」、追加時に「50件追加、100件表示中」などを簡潔に通知する。入力欄のフォーカスは検索のたびに移動させない。最終ページでボタンが消える場合の移動先を設計し、追加された記事を読み進められるようにする。本文へのスキップリンクを設け、日刊・検索・レビューごとに適切な見出し階層を用いる。

外部リンクが新しいタブで開くことを見た目と読み上げで伝え、繰り返される「記事を開く」のリンク先を記事名で識別できるようにする。現在のモード切り替えは `aria-pressed` 付きボタングループとして成立しているため、見た目だけを理由に `role="tab"` に置き換えない。

**受け入れ条件:** キーボードのみで検索・追加表示・記事への移動を完了できる。スクリーンリーダーで検索完了と追加件数が分かり、入力ごとの通知で操作を妨げない。最後の追加表示後もフォーカスを見失わない。見出し一覧から画面構成を把握できる。

## 05. 検索範囲の説明と絞り込み

**現状と根拠:** `syncDailyControls` は検索中の月と並び順を無効にする。検索結果には全期間・取得日の新しい順と説明するが、検索前には空白区切りのAND検索という説明がない。[parser.js](../parser.js) の `searchArticles` はキーワード一致のみを行う一方、既存インデックスには `theme`、`source`、`retrieved` がある。

**提案:** 検索欄の近くに「日刊を全期間から検索。空白で区切るとすべての語を含む記事を表示」と常時表示する。まずテーマと取得期間による絞り込みを追加し、適用中の条件・件数・「条件を解除」をまとめて示す。検索中に月選択を無効にする理由も説明するか、取得期間フィルタに役割を統合する。

**受け入れ条件:** キーワードとフィルタの組み合わせが一貫して適用され、0件時に条件を解除できる。日付条件は公開日ではなく取得日であると明記する。NFKC正規化、AND検索、重複URLの除外を維持する。検索状態のURL化（01）と整合させる。

**段階導入:** 情報源フィルタや週刊・月刊の横断検索は需要確認後にする。レビュー検索には別のインデックス設計が必要であり、現行の日刊検索に含まれると誤解させない。

## 06. 過去ログと前後の号への移動

**現状と根拠:** `renderMonth` は並び順を問わず最新日だけを開く。並び替えや他モードからの復帰でも再描画し、開閉状態を初期化する。週刊・月刊の期間移動は選択欄のみ。

**提案:** 月・日をキーに、同一ページ内で開閉状態を保持する。「すべて開く／閉じる」と日付への移動を追加する。古い順で読む場合は先頭側を開くなど、初回の展開ルールも見直す。週刊・月刊には「前の号／次の号」を設け、一覧に実在する号だけをたどる。

**受け入れ条件:** 日を開いて並び替え・モード切り替えをしても閲覧箇所を失いにくい。最古・最新では移動できない方向が分かる。欠号や年をまたぐ場合でも、日付計算で存在しないファイルへ移動しない。

## 07. AIレビューの来歴表示と目次

**現状と根拠:** `renderReview` は概況・トピック・出典を描画し、AI生成の注記とモデル・元記事数・入力件数・生成日は末尾の `review.notes` に表示する。[scripts/weekly.py](../scripts/weekly.py) と [scripts/monthly.py](../scripts/monthly.py) がこれらを出力済み。出典リンクは既にあるため、新規に出典を付ける提案ではない。

**提案:** 冒頭で「AIによる振り返り」と生成日を示し、詳細な生成情報は末尾に残す。本文は記事全文ではなく収集済み公開情報を材料にした要約であることを説明する。トピック見出しから短い目次を作り、本文・出典まで移動できるようにする。対象期間の日刊ログへ戻る導線も設ける。

**受け入れ条件:** 読み始める前にAI生成であると分かり、対象期間と生成日を区別できる。元記事数と入力件数が異なる場合も、すべての記事を要約したと誤解させない。目次はキーボードで利用でき、同名のトピックにも一意な移動先を付ける。

**実装上の注意:** 来歴の項目別表示が必要になった段階で生成側・パーサーの互換性を設計する。既存レビューの注記は自由文なので、現在の表示文字列の分割だけに依存しない。01のハッシュ形式と目次リンクが衝突しないようにする。

## 08. 新着日と収集状態の区別

**現状と根拠:** `renderMonth` の「最新」は選択月内の最新記事日に付く。カードの `published` はラベルなしの日付、`retrieved` は補助情報に表示する。収集処理は新着がないと日刊ログを追加しないため、記事の日付だけでは収集停止か新着なしなのか判定できない。[.github/workflows/collect.yml](../.github/workflows/collect.yml) では検索インデックス更新の失敗を許容するため、日刊と検索に差が生じる可能性もある。

**提案:** 現行データで可能な範囲では「この月の最新」「公開日」「取得日」と役割を明示する。次の段階で、収集の最終成功時刻・新着件数と検索インデックスの更新状態を公開用の小さなメタデータにし、UIで区別する。

**受け入れ条件:** 新着0件の収集成功を記事追加日と区別できる。インデックス更新失敗時に日刊収集の成功を取り消さない。時刻は日本時間と明記し、公開データにキーや詳細なエラー応答を含めない。状態が不明なときは「不明」とし、直近の記事日付から成功・失敗を推定しない。

**依存:** 後半は収集ワークフローとデータ形式の変更が必要。静的UIだけで現在のジョブの稼働状態を保証することはできない。まず日付ラベルの改善から着手する。

## 09. 記事の保存・再訪

**現状と根拠:** カードは元記事へのリンクとメタデータを表示し、保存機能はない。収集側の `data/seen.json` は重複収集を防ぐためのデータであり、利用者の既読情報ではない。

**提案:** 需要を確認したうえで「あとで読む」を端末内に保存し、保存一覧を用意する。最初はアカウントや端末間同期を導入せず、検証済み記事URLを識別子にする。保存一覧の書き出し・消去も提供する。

**受け入れ条件:** 再読み込み後に保存一覧が復元される。保存領域が使えない場合も閲覧を継続できる。端末内のみの保存で、ブラウザのデータ消去で失われることが分かる。記事を開いただけで「読了」にせず、サイト側データを個人の既読管理に転用しない。

## 10. RSS / Atomによる購読

**現状と根拠:** [README](../README.md) の閲覧・出力手順はPagesとMarkdownを中心とし、現在のチェックアウトにフィード生成処理はない。日刊・週刊・月刊の一覧と原稿は既にある。

**提案:** まず週刊・月刊のフィードを静的ファイルとして生成する。記事の公開URL、対象期間、短い紹介、AI生成の明示、安定したIDを含める。日刊は件数が多くなるため、日ごとのまとめか個別記事かを利用者に確認して追加する。初期段階でメール配信や個人情報の管理は導入しない。

**受け入れ条件:** 既存データからAPIなしで生成でき、再実行しても同じ号を別記事として配信しない。一般的なフィードリーダーで購読でき、日本語・特殊文字が正しく表示される。掲載するリンクは公開サイトのものとし、生成側で基準URLを設定する。

**依存・注意:** 現状のレビューURLはJavaScriptで表示するハッシュ形式。リーダー内で読める紹介文をフィードに持たせ、01のURL設計と整合させる。配信先によるハッシュリンクの扱いも確認する。改訂時にIDを変えず更新時刻を変えるルールを決める。

## 11. 日刊・週刊・月刊の横断検索

**現状と根拠:** [scripts/search_index.py](../scripts/search_index.py) は日刊ログのみを対象にする。レビューは `parseReview` で見出し・本文・実務への示唆・出典を読み取れるが、現行検索には含まれない。

**提案:** レビュー用インデックスを別途生成し、「すべて／日刊／週刊／月刊」で検索対象を選ぶ。レビュー結果は個別記事カードと区別し、号・対象期間・一致した見出しを表示する。日刊の出来事と、同じ出来事を扱うAI要約を混同させない。

**受け入れ条件:** 本文・実務への示唆にしかない語からもレビューに到達できる。結果に種別が示され、出典へ進める。日刊だけの検索では従来の正規化・AND検索を維持する。レビューの対象期間と生成日を混ぜて並べず、採用した並び順を明示する。

**依存:** 01・05のURLとフィルタ設計に合わせる。インデックスは既存Markdownから再生成し、追加のAI呼び出しは不要とする。

## 12. 自治体・地域・業務分野からの探索

**現状と根拠:** [config/queries.yml](../config/queries.yml) のテーマは「自治体DX」「自治体の生成AI活用」の2つ。日刊と検索データに自治体コードや地域・業務分野の専用項目はない。タイトルのキーワード検索だけでは表記ゆれや同名の自治体を整理しにくい。

**提案:** 窓口、庁内業務、防災など少数の業務分野から始め、明示的な根拠がある場合だけタグ付けする。自治体名は都道府県・市区町村を区別し、必要になった段階で公的な自治体コードと対応させる。「不明／複数自治体」を許容し、既存記事にも後から適用できる派生メタデータにする。

**受け入れ条件:** 名称が似た別自治体を混同しない。タグ未付与の記事も通常検索で見つかる。分類辞書・版・手動修正を管理でき、修正が再生成で失われない。サンプル記事で分類の妥当性を確認してから一括適用する。

**依存・注意:** 記事本文は取得しない方針を維持し、タイトル・説明文で判断できない所属や導入状況を推測で断定しない。AI分類を採用するなら17の費用枠と評価を先に定める。

## 13. 根拠付きの動向ダッシュボード

**現状と根拠:** 検索インデックスに取得日・テーマ・情報源があるため、既存データだけでも月別の収集件数は計算できる。一方、Braveの検索語・上位件数・取得時期と関連性フィルタの影響を受けるデータであり、自治体全体の網羅的な統計ではない。

**提案:** 最初はテーマ別の月次収集件数と、その集計対象の記事一覧を示す。12の分類が安定してから分野別の比較を追加する。数字やグラフから元記事へ遷移できるようにし、「収集記事数」であると明示する。

**受け入れ条件:** グラフと表の値が一致し、集計期間・取得日基準・件数定義を確認できる。検索語や判定方式の変更点を残し、変更前後をそのまま増減比較させない。小さい標本から「自治体の導入率」「社会全体の普及」を推定しない。

**注意:** 同一話題の転載が複数記事になるため、記事数と出来事数は区別する。15でグループ化しても、候補判定の不確実さを表示する。

## 14. 選択記事の資料向け書き出し

**現状と根拠:** `renderCard` にはタイトル・URL・情報源・取得日などがあるが、複数記事の選択や書き出しはない。業務での転用には元記事を個別にコピーする必要がある。

**提案:** 検索結果から選んだ記事の出典一覧をMarkdownまたはCSVで保存する。タイトル、URL、情報源、公開日、取得日を含め、未提供の公開日を補完しない。最初は画面内の選択だけで利用できるようにし、09の永続保存を必須にしない。

**受け入れ条件:** 画面で未表示の検索結果を勝手に選択しない。選択件数が確認でき、再選択や解除ができる。日本語、改行、引用符が壊れず、CSVを表計算ソフトで開いた際の数式としての解釈も防ぐ。記事本文や、存在しない生成AIの要約を付加しない。

**追加検討:** 週刊・月刊に印刷用CSSを加え、操作欄を除いた本文と出典をPDF保存しやすくする。印刷で出典URLが失われないことを確認する。

## 15. 訂正・編集注と関連記事の整理

**現状と根拠:** [scripts/topic_dedup.py](../scripts/topic_dedup.py) はタイトル類似度に基づく同一話題候補を観測するが、現在のUIは候補を表示しない。レビューには構造検証と出典があるが、内容の事実確認や訂正受付を代替するものではない。

**提案:** サイトに連絡・訂正依頼の入口を示し、当初はGitHub Issuesなど既存の運用先を利用する。ログのURLまたはレビューの号を指定できるテンプレートを用意し、公開投稿に機密情報を含めないよう案内する。訂正理由・日付を編集注として管理し、再生成時の扱いを明文化する。

関連記事は候補グループとして折りたたんで表示し、全記事を展開できるようにする。検出結果だけで元記事や `seen.json` を削除・統合しない。

**受け入れ条件:** 修正前後と理由がGitの履歴で追える。編集注が再生成で消えないか、上書き前に検出できる。誤った候補グループを解除でき、別自治体や別の施策を同一話題と断定しない。

**依存:** グループ情報をUIに渡す派生データと、人が修正する上書き情報を分離する設計が必要。訂正窓口は管理者が対応できる範囲で公開し、対応時間を根拠なく約束しない。

## 16. API不要のデータ整合性検査と画面テスト

**現状と根拠:** [.github/workflows/test.yml](../.github/workflows/test.yml) はAPI不要の `unittest` を実行する。既存テストは収集・生成処理とNode経由のパーサー・検索関数を検証しているが、実ブラウザでの画面操作は含まれない。検索インデックス更新は収集ワークフローで失敗を許容している。

**提案:** 読み取り専用の検査コマンドを設け、月・週・月刊の一覧と実ファイルの対応、検索インデックスとログの一致、パース可能性を検査する。更新済みファイルを比較するために、テストが追跡データを直接再生成・上書きする方式は避ける。API不要のローカル配信とブラウザ操作テストもCIに追加する。

**受け入れ条件:** 一覧の参照先欠落やインデックスの更新漏れを、対象ファイル名付きで検出できる。テスト後の作業ツリーが変わらない。検索、IME、モード切り替え、通信失敗、追加表示、01の履歴復元を代表的な画面テストで確認できる。テスト用に実APIキーを要求しない。

**注意:** 過去データの不備はまず検出結果を確認し、自動削除で整合させない。ブラウザ用依存と実行環境を明示し、既存の軽量な単体テストと分けて失敗原因を把握できるようにする。

## 17. 収集語・関連性判定・API利用量の評価

**現状と根拠:** [scripts/collect.py](../scripts/collect.py) は検索語最大10件、各上位10件、Jev最大20回、失敗時は候補を残す仕組みを持つ。現在の設定は5検索語。[scripts/weekly.py](../scripts/weekly.py) と月刊には入力件数制限、最大2回のAPI試行、トークン数のログがある。上限や費用対策は既に存在するため、無制限な収集拡張や再試行追加は提案しない。

**提案:** 検索語別の取得・新規・重複・除外件数と、AI呼び出し・トークン数を集計する。小規模な人手判定済みサンプルで関連性判定の見逃し・誤除外を評価し、検索語やしきい値の変更前後を比較する。まず過去のサンプル応答を使うオフライン評価から始める。

**受け入れ条件:** キー・リクエスト本文を記録せずに利用量を把握できる。API実測回数と集計値が一致する。Jevの判定品質とBraveの検索網羅性を混同しない。料金単価が変わり得ることを明記し、トークン数をそのまま確定請求額と呼ばない。

**依存・注意:** ライブ比較は追加のAPI利用を伴うため、実施前に上限を定める。完全な正解集合がない段階で「網羅率」を断定せず、サンプル内の指標として扱う。収集語・モデル・判定条件の版を記録し、13の集計解釈にも使う。

## 18. 再生成・障害復旧・依存関係更新の手順整備

**現状と根拠:** READMEには通常実行、欠号補完、`--force`、モデル変更などの説明がある。週刊・月刊は生成済みならスキップし、再生成は上書きを伴う。Python依存は `PyYAML>=6.0,<7`、CIはPython 3.12だが、Nodeを使うテストはNode不在ならスキップされる。

**提案:** 既存説明を土台に、401/403、モデル未提供、429、タイムアウト、不正な出力、検索インデックス更新失敗ごとの復旧判断を短い運用手順にまとめる。再生成前の差分・編集注・費用の確認、派生データだけの再構築、過去版へ戻す手順を明記する。CIではNodeの必要バージョンを明示し、意図しないスキップを把握する。

依存更新は自動通知・PRで受け取り、テスト後に取り込む。PyYAMLの範囲指定を維持するか、再現用の固定ファイルを追加するかは更新手順とセットで選ぶ。

**受け入れ条件:** APIを呼ばない復旧と有料APIを再実行する復旧を区別できる。認証・設定エラーを無条件に再試行しない。入力や既存ログを残したまま派生インデックスを復元できる。依存更新時に予定したPython・Nodeのテストが実行され、スキップを成功件数に含めない。

## 推奨する実装順と確認方法

1. **小さく改善し、基盤を固める:** 02の再試行、03の全文展開、08の日付ラベル。16の整合性検査と18の復旧手順も先行し、追加機能の前提を整える。
2. **状態と操作を整える:** 01と04を組み合わせ、URL・履歴・フォーカス・読み上げの挙動を定義する。06の開閉状態も合わせて扱う。
3. **探す・読み進める・活用する:** 05のフィルタ、06の号移動、07の来歴・目次、10の購読、11の横断検索、14の書き出しを段階的に追加する。
4. **編集と運用を改善する:** 08の公開用メタデータ、15の訂正・関連記事、17の評価を整える。
5. **需要と品質を確認して拡張:** 09の保存、12の分類、13の動向表示を検討する。分類を使う集計は、分類品質の評価後に導入する。

実装時は既存のPython/Node連携テストを維持し、変更した挙動に合わせて検証を追加する。パーサーの単体テストだけでは、`app.js` のDOM・履歴・フォーカス操作は検証できないため、該当変更ではブラウザ操作の確認が必要。

| 確認場面 | 確認する内容 |
| --- | --- |
| 日本語の検索 | IME確定後の検索、全角・半角、複数語、0件、51件以上の追加表示 |
| 遅い通信・取得失敗 | 一覧・本文・検索それぞれの再試行、連続切り替え、古い応答の破棄 |
| URLと履歴 | 直接アクセス、再読み込み、共有、戻る・進む、不正な期間・検索語 |
| 狭い画面と文字拡大 | 幅320pxを含む画面、200%拡大、長い見出し・検索語・出典名、全文展開 |
| キーボードと読み上げ | スキップリンク、見出し、検索件数通知、最終追加後のフォーカス、外部リンク |
| レビューとデータ | 空一覧、欠号、年またぎ、注記を含む既存Markdownとの互換性 |

改善効果は、代表的な検索課題で目的の記事にたどり着くまでの操作数、通信失敗後に復帰できるか、共有先で同じ表示を再現できるかで確認する。初期段階は少人数の操作確認で十分とし、アクセス解析サービスの追加を前提にしない。

検索インデックスは調査時点で約74KBのため、即座の分割配信や検索サーバー導入の優先度は低い。データ増加後に初回検索の転送量・処理時間を測定して判断する。同一話題の記事の自動非表示も、現在は検出のみという設計を維持し、誤判定の影響を評価してから検討する。
